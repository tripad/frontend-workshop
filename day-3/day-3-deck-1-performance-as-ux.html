Performance as UX

The thing we breezed past on Day 1.

On Day 1 we listed performance as a constraint of the web. We moved on quickly. If this were a longer course, we'd spend half a day here.

Quick version: performance isn't an engineering problem you hand off. It's a UX problem you author. The kilobytes you ship, the order you ship them in, the way your interface responds while waiting — these are design decisions, made by you, on every project.

The reframe

Performance is the third side of design.

Aesthetics. Usability. Performance.

Aesthetics

Usability

Performance

You already think about aesthetics — does it look right. You already think about usability — does it work.

Performance is the third side. Does it work fast enough that the first two matter?

Every kilobyte you ship is a design decision. The image you chose. The font weights you loaded. The animation library you didn't need. The twelve components your AI imported when you needed two. Pages don't get heavy by accident — they get heavy because someone, somewhere, didn't decide.

If your page is slow, your design is slow. There's no separation.

The headline reference

There are three kinds of slow.

Each needs a different design response.

Most designers think there's one kind of slow ("the page takes a while"). There are three. They have different causes and different fixes — and the fix is always a design move, not just an engineering one.

01

Actually slow.

The page is too heavy. The work is too much.

Fix: cut.

02

Perceived slow.

The work is happening. The UI doesn't show it.

Fix: communicate.

03

Intermittently slow.

The network drops. The server hiccups.

Fix: degrade gracefully.

The next three slides take each in turn.

Kind 01

Actually slow.

The page is too heavy. Cut.

The hero image is 4MB. The font has nine weights when you used two. The animation library is 200KB but you used one transition. The page is 8MB before any user data has loaded.

This isn't an engineering problem to fix later. It's a design audit problem to catch now. The fix is less.

Design audit

A few diagnostic questions

  • →Is the hero image really that big, or did you upload the original?
  • →Are you loading nine font weights when you use Regular and Bold?
  • →Did your AI import a chart library to render two numbers?
  • →What's your total page weight? You can check it in 10 seconds — coming up.

Kind 02

Perceived slow.

The work is happening. Show it.

A 2-second wait with a skeleton screen feels faster than a 1-second wait with a blank screen.

This isn't a trick. It's showing the user that their click registered. Motion — even fake motion — feels like progress. Silence after a tap feels like the app broke.

  • →Skeleton screens — the placeholder shape of what's loading
  • →Optimistic UI — assume the action worked, reconcile if it didn't
  • →Instant interaction feedback — the button reacts in 0ms, even if the result takes 800ms

The corollary: a loading state is a brand moment, not a fallback. Zomato's order tracking, Swiggy's delivery states, Notion's optimistic sync, Slack's send feedback — these aren't engineering details, they're brand decisions. The default spinner is a designer giving up.

Kind 03

Intermittently slow.

The network broke. Now what?

Performance is not only load speed. It is what the interface does when the network stops cooperating.

Real users lose signal mid-action. Servers timeout. APIs return errors. When the happy path breaks, the UX still has a job: preserve what the user did, explain what changed, and offer a next step.

Three states most designs forget

  • →Offline mode — what's still usable when the network is gone?
  • →Retry affordances — when something fails, can the user try again without starting over?
  • →Stale data — the data they're seeing is ten minutes old. Do they know?

After the audit

Two numbers worth caring about.

You don't need to memorize the rest.

LCP

Largest Contentful Paint

When does the main content appear?

Under 2.5s = fine. Over 4s = your user already gave up.

CLS

Cumulative Layout Shift

Does the page jump around as it loads?

Every layout shift is a designed-by-accident moment. Aim for almost zero.

These are starter metrics, not a curriculum. Knowing they exist, that they're measurable, and that your design decisions move them — that's enough for now.

Takeaway

Performance is design.

Not later. Not someone else's job. Yours.

You can ship a beautiful, perfectly accessible, semantically correct page that no one will ever see — because they closed the tab before it loaded.

If your design loads slowly, your design is slow.

The good news: now you know to look. That's most of the job.
